# Parallel Word Counting in a Text Corpus with MPI

## 1. Problem Description

Count how many times each word in `dataset/consulta.txt` (200 words, one per
line) appears in a corpus of 3000 text files `dataset/file_XXXX.txt`
(44,951,458 tokens in total), and report the 10 most frequent query words.

Three implementations are compared:

| Program | Strategy |
|---|---|
| `baseline_secuencial.py` | Sequential reference (provided) |
| `mpi1.py` | MPI v1: `bcast` of the query + static distribution in contiguous blocks of files |
| `mpi2.py` | MPI v2: size-aware static distribution (LPT) + parallel size scan |

The corpus is generated by `generator.py` (seed 42, so it is reproducible).
It has heterogeneous file sizes (about 60 % small, 30 % medium and 10 % large
files) and a skewed word distribution, which is why distributing files by
count can leave some processes with more work than others.

## 2. Environment and Execution Instructions

**Hardware/software:** HP 14-dq2504la, Intel Core i3-1115G4 (2 physical cores /
4 threads), 16 GB RAM, Windows 11, Docker Desktop (WSL2), image
`augustosalazar/slim-mpi:2`. The project folder is inside OneDrive and is
mounted into the container with a bind mount.

All commands are run from the repository root in PowerShell.

### a. Experimental plan

1. Generate the dataset with `generator.py`.
2. Run the sequential baseline 5 times. The first run is a cold-cache warm-up
   and is excluded from `T_seq` (it is reported anyway).
3. Choose `p` with `Detectar_procesos_mpi.py` (result: `p = 4`).
4. Run MPI v1 with `p = 4`, 5 runs. Record total time, per-process setup and
   local times.
5. Run MPI v2 under the same conditions, 5 runs.
6. Compute, for each version:
   - `T_p` = mean total time,
   - `S_p = T_seq / T_p`,
   - `E_p = S_p / p`,
   - `LI = max(t_i) / mean(t_i)`, with `t_i` the local counting time of
     process `i` (and the optional relative spread `(max - min) / mean`).
7. Check that every run reproduces the baseline output.

### b. Sequential baseline

`baseline_secuencial.py` (provided, unchanged) loads the query words into a
set and iterates over every `file_*.txt` in `dataset/`. For each line it
splits the text into tokens, lowercases them and, for every token that is in
the query set, increments a `Counter`. It prints the elapsed time (measured
with `time.perf_counter` around the counting), the top 10 words, and writes
`dataset/baseline_results.csv`.

```powershell
docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 python /app/baseline_secuencial.py
```

### c. MPI version 1

`mpi1.py` follows the steps of the assignment:

1. rank 0 reads `consulta.txt`;
2. rank 0 broadcasts the query words (`comm.bcast`);
3. rank 0 lists the `file_*.txt` files (sorted);
4. the files are split into `p` contiguous blocks whose sizes differ by at
   most one file, and distributed with `comm.scatter`. This balances the
   number of files, not the amount of work;
5. each process counts the query words in its own files (same counting logic
   as the baseline);
6. partial results are collected in rank 0 with `comm.gather`;
7. rank 0 merges them, prints the top 10 and compares the result with
   `dataset/baseline_results.csv`.

Timing: the clock starts after a `Barrier` and stops in rank 0 after the merge,
so it includes everything except process launch. Each process also reports its
number of assigned files, tokens, `setup_time` (everything before counting
starts) and `local_time` (counting only). The program prints `LOAD_IMBALANCE_LI`,
`RELATIVE_SPREAD`, `MATCHES_BASELINE` and `EXECUTION_TIME=<seconds>`.

### d. Test procedure

```powershell
# 1. Dataset
docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 python /app/generator.py

# 2. Baseline (5 runs; the first one is the warm-up)
docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 python /app/baseline_secuencial.py

# 3. Choice of p
docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 python /app/Detectar_procesos_mpi.py

# 4. MPI v1 and v2, p = 4, 5 runs each (logs in logs/mpi1 and logs/mpi2)
mkdir logs\mpi1 -Force
1..5 | ForEach-Object { docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 mpirun --allow-run-as-root --oversubscribe -np 4 python /app/mpi1.py | Tee-Object -FilePath "logs\mpi1\mpi1_run$_.log" }
mkdir logs\mpi2 -Force
1..5 | ForEach-Object { docker run --rm -v "${pwd}:/app" augustosalazar/slim-mpi:2 mpirun --allow-run-as-root --oversubscribe -np 4 python /app/mpi2.py | Tee-Object -FilePath "logs\mpi2\mpi2_run$_.log" }
```

**Correctness check.** Every MPI run compares its global counts with
`dataset/baseline_results.csv` and prints `MATCHES_BASELINE=True`; all 10 MPI
runs reported `True` and the same top 10 as the baseline.

**Note on `run_all.sh`.** The provided script can also run everything
(`NP_LIST=4 sh /app/run_all.sh`). It reads times with `grep "EXECUTION_TIME="`,
and the provided baseline prints `Tiempo de ejecución:` instead, so the baseline
row of its summary CSV stays empty. `T_seq` was therefore recorded manually
from the baseline output. The script also deletes and recreates `results/`,
which is why the logs used in this report are stored in `logs/`.

### c. Load imbalance evidence (v1)

Mean over the 5 runs:

| Rank | Files | Tokens | Mean local time (s) |
|---|---|---|---|
| 0 | 750 | 10,803,859 | 16.57 |
| 1 | 750 | 12,156,824 | 17.77 |
| 2 | 750 | 10,816,979 | 16.49 |
| 3 | 750 | 11,173,796 | 17.13 |

Mean **LI = 1.047** (range 1.032-1.059) and mean relative spread = 0.083.
Rank 1, which received the most tokens (12.16 M against about 10.8 M for ranks
0 and 2), was the slowest process in all 5 runs. All processes got 750 files, so
the imbalance comes from file sizes, not from file counts.

The mean setup time was 6.59 s (27 % of T_p). It is almost identical in the
four ranks, because rank 0 reads the query and lists the files while the others
wait for the `scatter`.

### d. MPI version 2: how it corrects the imbalance, and its results

**Design.** Version 2 changes two things:

1. *Size-aware assignment (LPT).* Files are sorted by size in bytes and each one
   is given, largest first, to the process with the fewest assigned bytes. Every
   process computes the same deterministic assignment from the same sizes, so no
   `scatter` is needed.
2. *Shorter sequential setup.* Rank 0 only lists file names (one `listdir`, no
   per-file `isfile`). The `getsize` calls are split among all processes (750
   files each) and shared with `allgather`. This targets the setup time measured
   in v1.

**Timing results (p = 4).**

| Run | Total (s) | Setup (s) | Max local (s) | LI |
|---|---|---|---|---|
| 1 | 22.158 | 1.38 | 20.765 | 1.0074 |
| 2 | 21.320 | 1.59 | 19.726 | 1.0158 |
| 3 | 19.587 | 1.88 | 17.709 | 1.0083 |
| 4 | 18.155 | 1.54 | 16.620 | 1.0076 |
| 5 | 18.269 | 1.33 | 16.938 | 1.0117 |

**T_p = 19.90 s** (std 1.80 s), **S_p = 34.39 / 19.90 = 1.73**,
**E_p = 0.43**, mean **LI = 1.010**. A separate test run (17.62 s) done before
the 5 reported runs is not included; including it would give T_p = 19.52 s.

Bytes per process are equal to within 50 bytes (about 68.76 MB each) and tokens
to within 0.02 % (about 11.24 M each).

**Comparison v1 vs v2 (p = 4, T_seq = 34.39 s).**

## 4. Analysis

### a. Parallel performance

Yes, both MPI versions improved on the sequential baseline, but neither is
close to the ideal `S_p = p = 4`. v1 reached S_p = 1.41 (E_p = 0.35) and v2
reached S_p = 1.73 (E_p = 0.43).

The gap to the ideal can be split into measured components. The ideal time with
4 processes is 34.39 / 4 = 8.60 s.

| Component | v1 (s) | v1 share of gap | v2 (s) | v2 share of gap |
|---|---|---|---|---|
| Gap to ideal (T_p − 8.60) | 15.75 | 100 % | 11.30 | 100 % |
| Sequential setup | 6.59 | 42 % | 1.54 | 14 % |
| Counting phase, mean time (above 8.60) | 8.39 | 53 % | 9.57 | 85 % |
| Load imbalance (max − mean local) | 0.78 | 5 % | 0.18 | 2 % |

- **Hardware.** If the setup is left out, the speedup is
  34.39 / 17.77 = 1.94 for v1 and 34.39 / 18.35 = 1.87 for v2, close to the 2
  physical cores of the i3-1115G4. The two extra hardware threads do not behave
  like two extra cores, and the sum of local times (about 68 s in v1 and 73 s in
  v2) is about twice the sequential time. This is the dominant limit and no
  distribution strategy can remove it. The counting-phase row above lumps
  together hyper-threading, file I/O through the Docker bind mount and
  virtualization; this experiment did not separate them.
- **Sequential setup.** In v1, about 27 % of the total time is spent before
  counting starts, mostly in rank 0 (listing the files with one `isfile` call
  per file) while the other ranks wait. The data transfer itself (`bcast`,
  `scatter`) is tiny, so the file-system calls are the likely cause. This is an
  inference from the timings, not an isolated measurement.
- **Amdahl-type effect.** Part of the work (setup, final merge) does not scale
  with `p`, and the communication and merge cost after counting is negligible
  (total ≈ setup + max local time in every run).

### b. Load balance

**Evidence in v1.** All processes received 750 files, but the token count per
process ranged from 10.80 M to 12.16 M. The slowest process was rank 1 (the one
with the most tokens) in all 5 runs, with local times of 16.4-21.6 s against
14.5-20.5 s for the fastest. The mean LI was 1.047 (1.032-1.059) and the
relative spread 0.083. So the imbalance is real and consistent, but small. Even
perfect balance would only lower the slowest process by about 0.78 s, about 3 %
of T_p. Tokens predict the order of the processes but not the exact times
(token ratio 1.082 against time ratio 1.047).

**Did v2 reduce it?** Yes: LPT made bytes per process equal within 50 bytes and
tokens within 0.02 %, and LI dropped from 1.047 to 1.010.

**Did that produce a real performance improvement?** v2 is faster overall
(T_p 24.35 s to 19.90 s, 18 % less), but the improvement does not come from the
better balance:

- The setup dropped by 5.05 s (6.59 s to 1.54 s), which is more than the whole
  4.45 s reduction in T_p. The setup times of the two versions do not overlap
  (5.5-7.9 s in v1, 1.3-1.9 s in v2), so this is the robust result.
- The balance could save at most 0.6-0.8 s, which is below the run-to-run noise
  (std 1.8-2.9 s). Meanwhile the counting phase was on average 0.58 s slower in
  the maximum and 1.18 s slower in the mean in v2. The cause was not isolated
  (see limitations).
- A Welch t-test on the total times gives t ≈ 2.9 with 5 runs per version, which
  is moderate evidence that v2 is faster, not conclusive.

The honest answer is that v2 gave a real improvement, but as a consequence of
reducing the sequential setup, and the load-balancing part alone is not
measurably distinguishable from noise in this experiment.

### c. Limitations

| Limitation | Effect on the conclusions |
|---|---|
| **Hardware: 2 cores / 4 threads laptop.** Speedup is capped near 2, whatever `p` is. | Strong. It explains most of the gap to `S_p = 4`, so the low efficiency (0.35-0.43) says little about the quality of the algorithms. Results do not transfer to a machine with 4 physical cores. |
| **Docker Desktop + WSL2 + OneDrive bind mount.** File I/O and metadata calls are slow and variable. | Strong on the setup times (the main finding), and probably on the counting phase. The size of the v1 to v2 improvement depends on this file system; on a local disk the setup would likely be smaller. |
| **Noise and few runs (5 per version).** Std is 11 % for the baseline, 12 % for v1 and 9 % for v2; both MPI series drift downward within the batch. The first baseline run (110 s) shows how cold caches distort timings. | Medium. The v1 vs v2 total time difference (4.45 s) is about 1.5-2 standard deviations. The 3 % effect of load balancing cannot be separated from noise. |
| **Non-interleaved runs.** v1 and v2 were run in two separate batches, so a slow drift (thermal, cache, background load) could favour one of them. | Medium. It could explain why the counting phase is 1.2 s slower in v2, and it may inflate or reduce the measured gap slightly. |
| **`T_seq` uncertainty.** Using the 4 warm runs (30.3-39.0 s) the speedup of v2 ranges from 1.52 to 1.96, and that of v1 from 1.25 to 1.60. | Medium for absolute speedup and efficiency; small for the ranking v2 > v1. |
| **Choice of p = 4 is weakly supported** (N = 4 only 1.27x faster than N = 1; N = 3 slower than N = 1), and only one `p` was tested. | Medium. No scalability curve; we cannot tell if `p = 2` would have given similar speedup with higher efficiency. |
| **Size in bytes is a proxy for work.** LPT balances bytes, not the real counting time; the setup attribution (listing cost) was inferred, not isolated. | Small to medium. It limits the maximum balance achievable and the explanation of where the setup time goes. |
| **Single synthetic dataset** (seed 42) and a single machine. | Small for this lab; the conclusions apply to this corpus only. |

## 5. Conclusions

For this problem and this machine I would recommend the v2 strategy
(parallel size scan plus LPT distribution by file size): it gave T_p = 19.90 s,
speedup 1.73 and efficiency 0.43 with LI = 1.010, against 24.35 s, 1.41, 0.35 and
LI = 1.047 for static block distribution in v1. However, the measurements
show that the gain came mainly from cutting the sequential setup from 6.6 s to
1.5 s, while the load-imbalance fix by itself was worth less than 1 s and is
within the noise, because the v1 block distribution was already nearly balanced
(LI = 1.047, 750 files per process). Both versions are far from the ideal
speedup of 4 mainly because the i3-1115G4 has only 2 physical cores (counting
alone reaches 1.87-1.94, about 2), so the main limit is the hardware and not the distribution
strategy. These conclusions come from 5 runs per version in non-interleaved
batches, on one machine and one dataset, so they are valid as evidence for this
setup but not as general performance claims.
